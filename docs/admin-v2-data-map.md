# Admin v2 data map — Stage 1

## Source and freshness rules

Verified from actual SQL/projections, not filenames. No production read audit or exported personal records was used. Synthetic fixtures are independently hand-calculated in tests/admin-safe-operations.test.mjs.

Every row below inherits this missing/error rule: show last successful data as stale; without cached data show unavailable/—, never a synthetic zero. Actual zero is valid only after a successful read. The operational summary is one primary D1 statement; list/total pairs use a primary batch. generatedAt is response time, NOT last business update; businessUpdatedAt=null is deliberate where no universal source exists. Existing Mailing/Funnel/history-detail projections retain their separate read boundaries; do not label them the same database-wide snapshot. The global Admin freshness label concerns the active operational context; optional Funnel has its own stale state.

E = selected event ID, not whichever event is currently public. Global queues never acquire an event filter accidentally. API identity uses sourceType=reservation/sourceId/memberId/eventId; the same manually recorded paid amount is not a second payment source.

Metric IDs are definitions for current screens and compatible later work, NOT new future APIs. “Informational” / “Stage 2/3” destinations are explicitly not implemented clickable metrics. No misleading link is introduced where the destination cannot express the exact population. Existing primary navigation is unchanged.

## Independent reconciliation

Two active reservations: approved due 1,000 / paid 200 / crew 2 / 1 cabin unit; pending due 1,000 / paid 1,300 / crew 4 / 2 requested cabin units. One cancelled record due 0 / paid 400 / crew 5.

- Active reservations 2; planned people 6 (not 11).
- Active due 2,000; all recorded paid 1,900; active paid 1,500; inactive paid 400.
- Outstanding 800; overpayments 700; applied to active obligations 1,200. Overpayment cannot cancel another member's debt.
- Confirmed occupancy 1 unit / 2 people, pending demand 2 units; 5 limited units + unlimited tent does not make a meaningful combined percentage.
- One history claim with both components pending contributes 1 queue item, 1 attendance component and 1 S&S component, not two members.
- Paginated reservation fixture: limit 1, returned 1, total 2, filtered pending total 1; reading a missing legacy VS performs zero writes.
- Deadline 2026-09-08 becomes overdue after 23:59:59 UTC with no row change. Cancelled paid remains in recorded cash and overpayments, not active due.

## Meaning intentionally not invented

D1 profiles are not a complete Firebase account census. Planned presence is not check-in. S&S interest is not a judged entry. Paid totals are manually recorded, not bank reconciliation. No refund/credit workflow or historical cash-flow/occupancy reconstruction. Opens are approximate, clicks are not replies; Mailing D answer metrics remain absent. No QR, member ranking policy, lifetime balance, Merch inventory or dashboard preferences added.

Existing Mailing contact linkage semantics are preserved for this task; Stage 2 must inspect canonical member links and ambiguous legacy email matches before exposing Member 360 navigation. No live contact correction/backfill has occurred.
